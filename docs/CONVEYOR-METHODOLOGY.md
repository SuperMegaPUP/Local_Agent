# МЕТОДОЛОГИЯ МУЛЬТИАГЕНТНОГО КОНВЕЙЕРА «СИМБИОЗ»

Версия 1.0 · Дата: 2026-08-28 · Статус: все три волны в бою
Автор: молодой (по поручению старшего)

Документ описывает методологию автономной разработки программного продукта
несколькими LLM-агентами без постоянного участия человека: концепцию,
архитектуру и детальную реализацию системы, которая за 3 дня выполнила
7 эпиков (61 карточка) проекта «Горизонт событий» (Next.js + TypeScript +
Prisma + Jest) на локальном vLLM-инференсе.

## 1. КОНЦЕПЦИЯ

### 1.1 Проблема

Автономный LLM-агент, которому дали задачу «сделай фичу», систематически
проваливается четырьмя способами:

1. **Имитация успеха.** Агент завершает ход словами «готово, всё работает»,
   не сделав реальной работы. Для LLM «сообщить об успехе» дешевле, чем
   сделать успех — без внешнего контроля это главная угроза качеству.
2. **Петли и зависания.** Агент зацикливается на одной команде
   (`npm install` → ошибка → `npm install` → ошибка…), либо «жив» формально,
   но не производит токенов. Таймауты здесь бесполезны: петляющий процесс
   выглядит здоровым.
3. **Крахи и рассинхроны.** Процесс падает, узел теряет сеть, движок
   инференса зависает. Часть состояния теряется, «running»-карточки
   превращаются в сирот.
4. **Деградация среды.** Параллельные писатели ломают общее рабочее дерево,
   сломанный билд засоряет следующие шаги, секреты попадают в коммиты.

Каждая из четырёх проблем требует своего класса защиты. Ни «более умный
промпт», ни «более сильная модель» их не снимают: они вероятностны, а
потребность — детерминированная.

### 1.2 Ключевой принцип: симбиоз

**LLM решает, детерминированный код судит.**

Распределение ответственности:

| Кто | Что делает | Почему |
|---|---|---|
| LLM-агент (воркер) | Генерирует гипотезы: код, планы, ответы | Единственный способ создавать новое |
| Детерминированный код (шлюз, гейты, fastlane) | Проверяет факты: типизация, тесты, существование коммитов, секреты | Недорого, воспроизводимо, не врёт |
| Человек (старший) | Принимает решения на эскалациях, открывает «холодные окна» | Ответственность за необратимые действия |

Ни один результат воркера не становится фактом, пока его не подтвердил
не-LLM механизм. Воркер может написать в отчёте что угодно — система
проверяет каждую заявку отдельно:

- заявил коммиты → каждый хеш должен существовать в объектном хранилище git;
- заявил «тесты прошли» → гейты прогоняются заново независимо;
- заявил «готово» → карточка переводится в `review`, а не в `done`;
  `done` воркеру ставить запрещено протоколом.

Это не недоверие к модели — это инженерная граница: вероятностному компоненту
даётся свобода творчества, детерминированному — право вето.

### 1.3 Семь принципов

**P1. Канбан — единственный источник правды (SSoT).**
Всё состояние системы — одна SQLite-база: карточки, события, комментарии,
попытки, кулдауны. Любой участник (шлюз, воркер, fastlane, watchdog,
человек) общается с миром только через неё. Нет скрытых состояний в памяти
процессов: любой процесс можно убить и поднять — состояние восстановится
из БД.

**P2. Вероятностное предлагает, детерминированное утверждает.**
См. раздел 1.2. Все «судьи» в системе — скрипты: tsc, eslint, jest,
gitleaks, npm audit, git rev-parse. LLM выступает судьёй только на одном
опциональном уровне (семантическая верификация, слой C-L2) и там —
fail-open: ошибка верификатора не блокирует поток.

**P3. Экономика восстановления: дешёвое до дорогого.**
Когда воркер падает, система не тратит ресурс мгновенно. Лестница:
мягкий пинок (комментарий + перезапуск, бесплатно) → полноценный retry
(дорогой LLM-прогон) → blocked + эскалация человеку. Пинки не расходуют
бюджет retry'ов. Это экономит десятки дорогих прогонов на шумовых сбоях.

**P4. Baseline-aware: запрет регрессий, а не требование идеала.**
Гейты сравнивают текущее состояние проекта с зафиксированным базовым
состоянием (baseline). Проект с 38 известными находками gitleaks и 15
известными уязвимостями npm не «падает» — проходит, если не появилось
НИЧЕГО НОВОГО. Требовать «ноль ошибок» от наследуемого кода невозможно;
требование «не ухудшить» — исполняемо и достижимо. Улучшение (исправление
части baseline) тоже проходит.

**P5. Изоляция писателей.**
Параллельные кодеры не работают в общем дереве. Каждый писатель получает
собственный git worktree на собственной ветке; центральное дерево — зона
только гейтов и мержей. Мержи сериализованы архитектурно (однопоточный
цикл шлюза), конфликты эскалируются, а не молчат.

**P6. Наблюдаемость как первоклассный гражданин.**
Каждое действие оставляет след: журнал событий карточки (events),
комментарии, попытки (runs), логи процессов, hang_log, cooldowns.
Любой инцидент реконструируется постфактум по журналам. Анти-spam-фильтры
на алертах (10 минут на состояние) делают наблюдаемую систему пригодной
для жизни, а не оглушающей.

**P7. Обратимость и дисциплина окон.**
Любое изменение инфраструктуры: бэкап → применение в «холодном окне»
(ни одного активного воркера) → верификация → задокументированный откат
одной командой. Кодовые изменения дополнительно защищены ENV-тумблерами
(по умолчанию выключены): откат = снять тумблер, без возврата кода.

### 1.4 Карта угроз → защит

| Угроза | Класс | Защита (слой) |
|---|---|---|
| Имитация успеха | качество | TraceGuard L1/L2 (C), self-review (H), механические гейты |
| Петля команд | надёжность | loop-детектор (F) |
| Зависание без вывода | надёжность | heartbeat по mtime лога (шлюз) |
| Смерть процесса | надёжность | reconcile + adopt (шлюз), kill групп процессов |
| Зависание LLM-движка | среда | watchdog + cooldown (D) |
| KV-давление / деградация | среда | watchdog pressure-алерт (D) |
| Общий checkout ломается | среда | worktree-ферма (План B) |
| Конфликты мержей | среда | эскалация-карточка (План B) |
| Новые секреты в коде | безопасность | security_gate: gitleaks vs baseline (K) |
| Новые уязвимости зависимостей | безопасность | security_gate: npm audit vs baseline (K) |
| Выдуманные коммиты в отчёте | качество | TraceGuard L1: git rev-parse (C) |
| Отчёт не соответствует событиям | качество | TraceGuard L2: LLM-верификатор, fail-open (C) |
| Ревьюер верит автору | качество | self-review: только дифф, temp 0 (H) |
| Эпик закрыт без нужных проверок | процесс | декларативные required_gates (B) |
| Воркер вышел за рамки полномочий | процесс | allowed_tools (G) |
| Потеря состояния при крахе | надёжность | SSoT в SQLite + crash-adopt (P1) |
| Слоты сжигаются на больном движке | эффективность | cooldown-гейт запуска (D+E) |

## 2. АРХИТЕКТУРА

### 2.1 Топология

```
┌─ CONTROL NODE (Linux-виртуалка) ─────────────────────────────────────┐
│                                                                       │
│  kanban/boards/main.sqlite3  ← SSoT: cards, events, comments, runs,  │
│                                  cooldowns, hang_log, tool_calls,    │
│                                  failed_drafts, memories             │
│        ▲  ▲  ▲  ▲                                                      │
│        │  │  │  └─ fastlane.py (cron */5) — автоприёмка review       │
│        │  │  └───── watchdog.py (systemd) — контроль LLM-движка      │
│        │  └───────── kanban/cli.py — CLI людей и воркеров            │
│        └──────────── gateway.py (systemd) — диспетчер, 90с цикл      │
│                          │                                             │
│                          ▼ spawn (opencode run --agent <role>)         │
│                 воркеры: architect, coder, qa, code-reviewer,         │
│                 ui-reviewer, e2e, docs, controller, orchestrator      │
│                 каждый — свой git worktree (writers) + ветка wt/<id>  │
│                                                                       │
│  gates/ — baseline'ы: tsc, lint, jest, gitleaks, npm                  │
│  runs/  — логи воркеров, реестр pid, repo.lock                        │
└───────────────────────────────────────────────────────────────────────┘
        │ HTTP :9100 (/metrics, /restart)          ▲ OpenAI-compat :8000
┌───────────────────────────────────────────────────────────────────────┐
│ GPU NODE (192.168.31.52)                                              │
│  vLLM: qwen3.8-27b INT8, CMP 170HX 64GB                               │
│  watchdog-agent.py :9100 — nvidia-smi + vLLM-метрики + авто-рестарт   │
└───────────────────────────────────────────────────────────────────────┘
```

Принцип разделения: **детекция — наша, исполнение — чужое.** Контрольная
нода видит здоровье движка по HTTP-срезу (агент на GPU-ноде собирает
nvidia-smi + Prometheus-метрики vLLM) и сама никогда не трогает железо;
рестарт запрашивается у агента по токену.

### 2.2 Компоненты и их контракты

**gateway.py** (системный демон, цикл 90 с) — единственный, кто:
- двигает карточки по статусам (promote, запуск, сбор результатов);
- запускает и убивает воркеров;
- проводит гейты и мержи;
- применяет экономику восстановления.

Воркеры НЕ знают друг о друге и не управляют потоком — они выполняют одну
карточку и останавливаются. Весь поток — в шлюзе. Это делает систему
восстанавливаемой: убей шлюз — воркеры доделают своё, новый шлюз
подберёт их результаты.

**fastlane.py** (cron каждые 5 минут) — автоприёмка. Закрывает `review`
карточки в `done` по консервативным правилам (раздел 4.10). Отдельный
процесс, короткая транзакция, ретраи на «database is locked».

**watchdog.py** (системный демон, цикл 15 с) — контроль LLM-движка.
Пишет в ту же БД (cooldowns, hang_log). Шлюз читает cooldowns перед
запуском воркеров — связь компонентов идёт через БД, не через IPC.

**kanban/cli.py** — единый интерфейс записи в БД для людей и воркеров:
create/list/show/move/comment/mem/recall/ask. Схема БД определяется здесь
(SCHEMA-константа) — один владелец структуры.

**roles/** — профили ролей: SOUL.md (личность + протокол) на роль.
Роли выбираются воркером через `opencode run --agent <role>`; температуры
заданы в шлюзе (см. 4.4).

### 2.3 Жизненный цикл карточки

```
           ┌──────────────┐  все deps done   ┌───────────┐
  create → │     todo     │ ───────────────► │   ready   │
           └──────────────┘                  └─────┬─────┘
                                                   │ слот свободен,
                                                   │ cooldown снят
                                        ┌──────────▼──────────┐
                              ┌─────────│       running       │─────────┐
                              │         └──────────┬──────────┘         │
                    смерть/зависание/петля         │ ARTIFACTS +        │
                    (nudge→retry→blocked)          │ move review        │
                              │                    ▼                    │
                    ┌─────────┴──────┐      ┌───────────┐   ┌──────────▼──────┐
                    │    blocked     │      │  review   │   │     blocked     │
                    │ + escalation   │      └─────┬─────┘   │ (сам воркер)    │
                    └────────────────┘            │         └─────────────────┘
                                  гейты (шлюз)    │
                        ┌─────────────────────────┼──────────────────────┐
                        │ FAIL: revert мержа,     │ PASS: gates-passed   │
                        │ возврат в todo          ▼                      │
                        │                    ┌───────────┐               │
                        └───────────────────►│   done    │◄──────────────┘
                                             └───────────┘  fastlane
                                                          (автоприёмка)
```

Эпики — особые карточки: не запускаются как воркеры, закрываются шлюзом,
когда все дети done И декларативные гейты удовлетворены (слой B).

### 2.4 Слои защиты (реестр)

| Слой | Название | Волна | Где живёт | Режим |
|---|---|---|---|---|
| B | декларативные required_gates | 2 | gateway | в бою |
| C | TraceGuard L1 (коммиты) + L2 (семантика) | 2 | fastlane | L1 в бою, L2 опционально |
| D | watchdog движка + cooldown | 1 | watchdog | в бою |
| E | soft-nudge экономика | 1 | gateway | в бою |
| F | loop-детектор | 1 | gateway | в бою |
| G | allowed_tools per-card | 2 | gateway (промпт) | в бою |
| H | self-review | 3 | gateway (промпт) | в бою |
| J | consult (спрос у роли) | 3 | cli + gateway + fastlane | в бою |
| K | security_gate (gitleaks+npm) | 3 | gateway | в бою (тумблер ON) |
| I | vision для ui-reviewer | — | — | отложен (нужен VLM) |
| L | cloud fallback | — | — | отложен (нет потребности) |

Номера соответствуют PLAN-SYMBIOSIS.md; пропущенные номера — зарезервированы
или объединены.

## 3. РЕАЛИЗАЦИЯ

### 3.1 Канбан: схема данных

База: `kanban/boards/main.sqlite3` (SQLite 3.53, WAL, `PRAGMA foreign_keys=ON`).

**cards** — ядро:

```
id, title, description,
kind          — epic | task | escalation | consult
assignee      — роль (architect, coder, qa, code-reviewer, ui-reviewer,
                e2e, docs, controller, orchestrator)
status        — todo | ready | running | review | done | blocked
parent_id, depends_on(CSV),
timeout_minutes, retry_count, max_retries,
created_at, started_at, finished_at, heartbeat,
required_gates(TEXT CSV)  — слой B, миграция 001
allowed_tools (TEXT CSV)  — слой G, миграция 001
security_gate(INTEGER 0/1)— слой K, миграция 001
nudged        (INTEGER)   — слой E, миграция 001
```

**Вспомогательные таблицы:**
- `events(card_id, type, payload, created_at)` — журнал: created, ready,
  started, nudge, retry, gates-passed, gates-failed, gates-blocked, done,
  blocked, escalated…
- `comments(card_id, author, body, created_at)` — рабочие заметки и
  протокольные маркеры (ARTIFACTS:, ANSWER:)
- `runs(card_id, attempt, command, exit_code, output, started_at, finished_at)`
- `cooldowns(key, reason, until)` — ключи: `engine` (движок), `tool:*`, `worker:*`
- `hang_log(ts, action, gpu_util, kv_cache_pct, gen_tokens_60s)`
- `tool_calls`, `failed_drafts`, `memories` — аудит и память

**Миграции** (`kanban/migrations/`):
- `001_symbiosis.sql` — 4 колонки с DEFAULT + 4 таблицы. Совместимость
  назад: весь старый код работал без изменений (DEFAULT'ы).
- `002_consult_kind.sql` — расширение CHECK(kind) на `'consult'`.
  Технически — полная реконструкция таблицы (CREATE новой → INSERT SELECT →
  DROP → RENAME), потому что column-level unnamed CHECK в SQLite нельзя
  изменить ALTER'ом. Применялась на scratch-копии с полным регрессом
  (FK, индексы, значения W1-колонок пережили rebuild) до живой БД.

Правило применения: **scratch-копия → регресс → холодное окно → живая БД**,
бэкап перед каждым шагом.

### 3.2 Шлюз: цикл iter_cycle

Одна итерация (каждые 90 с, `POLL_SEC`) состоит из пяти фаз, идущих строго
последовательно в одной транзакционной единице:

**Фаза 0 — эпики.** Для каждого `epic` в todo/ready: все дети done?
Да → проверка декларативных гейтов (слой B): для каждой роли из
`required_gates` должна существовать дочерняя done-карточка с таким
assignee. Нет → эпик НЕ закрывается, недостающим ролям автоматически
создаются гейт-карточки (`[gate:<role>] <название>`, kind=task, todo),
событие `gates-blocked`. Да → эпик done.

**Фаза 1 — promote.** `todo → ready`, когда все `depends_on` done
(и родитель не blocked).

**Фаза 2 — живые воркеры.** Для каждого запущенного:
1. **Crash-adopt:** карточка `running` без записи в реестре pid
   (шлюз убили между записью реестра и commit БД) помечается `dead`
   и идёт штатным путём смерти.
2. **Heartbeat** = mtime лог-файла воркера (opencode пишет в него
   непрерывно). Свежий вывод = жив, даже если работает часами. Порог
   `HB_LIMIT_MIN=20`.
3. **Loop-детектор (F):** в последних 64 KB лога собираются строки вида
   `$ <команда>` (bash-вызовы opencode), нормализуются (whitespace →
   одиночный пробел, обрезка 200 символов). Одна и та же команда
   `LOOP_KILL=5` раз подряд → SIGTERM группе процессов (воркер запускается
   с `start_new_session=True`, имеет собственную pgid — убивается целое
   дерево, включая детей типа npm), далее штатный путь смерти.
   Консерватизм: только префикс `$ `, только хвост — пропущенную петлю
   всё равно возьмёт heartbeat.
4. **Путь смерти** (dead или stuck): экономика слоя E (раздел 4.3).

**Фаза 3 — гейты.** Для каждой `review`-карточки:
1. Writers (coder/qa) при включённом Плане B: мерж worktree в main
   (раздел 4.5). Центральный checkout грязен → мерж ОТЛАГается на
   следующий цикл (не ошибка!). Конфликт → `merge --abort`, карточка
   blocked, эскалация-карточка «РАЗБОР КОНФЛИКТА МЕРЖА».
2. `consult`-карточки (слой J): лёгкий штамп `gates-passed` без
   tsc/lint/jest и БЕЗ ARTIFACTS-маркера (иначе fastlane закрыл бы
   карточку до ответа воркера).
3. Обычные: `run_gates()` — tsc + eslint + jest, baseline-aware (4.6).
   При `security_gate=1` и тумблере `PIPELINE_SECURITY_SCAN=1` —
   дополнительный security-скан (слой K, 4.9).
4. PASS → комментарий-штамп `ARTIFACTS: mechanical gates PASSED`,
   событие `gates-passed`, cleanup worktree.
   FAIL → **revert мержа** (`git revert -m 1 HEAD` — main возвращается
   к прежнему состоянию), карточка в todo, комментарий с полным отчётом
   гейтов, событие `gates-failed`.

**Фаза 4 — запуск.** Сначала — cooldown-гейт: если в таблице cooldowns
живая запись `engine` → НИКАКИХ новых воркеров (активные не трогаются —
докрутятся сами или упрутся в heartbeat). Затем: слоты =
`MAX_PARALLEL − живые`, готовые карточки сортируются приоритетом
(orchestrator → architect → остальные, затем FIFO), writers получают
worktree (или fallback на общий checkout + flock), карточка → running,
`launch_worker()`.

**Запуск воркера:** `opencode run --agent <role> -m <model> "<prompt>"`
через `subprocess.Popen(start_new_session=True)`, stdout/stderr →
`runs/<card>-<n>.log`, pid в реестр `runs/workers.json` (атомарно:
tmp + rename). Реестр и БД — разные источники: БД говорит «что должно
быть», реестр — «кто запущен»; рассинхрон разбирается crash-adopt.

### 3.5 План B: worktree-ферма (изолирование писателей)

Проблема: два параллельных кодера в общем checkout ломают друг друга
(переменные файлы, git-индекс, незавершённые операции).

Решение — горячий тумблер (файл `PLAN_B`, hot-switch без рестарта):

1. **Подготовка.** Writer-карточка получает
   `git worktree add -b wt/<card_id> <dir> main` — копию дерева на HEAD
   main. Symlink `node_modules → центральный node_modules` даёт локальные
   tsc/jest без переустановки (компромисс задокументирован: npm install
   внутри worktree запрещён промптом, арбитр — центральный гейт).
2. **Работа.** Воркер коммитит в свою ветку. Промпт сообщает: «НЕ
   мержись сам — шлюз сделает после review».
3. **Мерж.** Фаза 3 шлюза: `git merge --no-edit wt/<id>` из центрального
   чекаута. Однопоточность цикла шлюза = естественная сериализация
   мержей. Три исхода: успех / центральный checkout грязен → defer на
   следующий цикл / конфликт → abort + blocked + эскалация.
4. **Отказ.** FAIL гейтов → `git revert -m 1 HEAD` (main чист),
   worktree сохраняется — воркер дорабатывает в той же изоляции.
5. **Cleanup.** Успех или blocked → `worktree remove --force` +
   `branch -D`.
6. **Recovery.** При старте шлюза: running-writers с потерявшимися
   worktree'ми восстанавливаются (`recover_orphan_worktrees`).
7. **Fallback.** Worktree не создался → старый режим: общий checkout +
   `fcntl.flock` на `runs/repo.lock` (один writer одновременно).
   Lock держится на открытом fd в словаре `held_locks` до смерти
   воркера — закрытый fd снял бы замок преждевременно.

### 3.6 Слой D: watchdog LLM-движка

Отдельный демон (systemd, цикл 15 с). Опрашивает `watchdog-agent.py`
на GPU-ноде (`:9100/metrics`): nvidia-smi (util, mem) + vLLM-метрики
(running, waiting, gen_tokens_60s, kv_cache_pct, preemptions_60s) +
health по `/v1/models`.

Три режима детекции:

| Режим | Условие | Действие |
|---|---|---|
| A. engine_down | `/v1/models` не отвечает | cooldown 60 с + hang_log + алерт |
| B. engine_stuck | running > 0 И gen_tokens_60s = 0 дольше 120 с | cooldown 60 с + hang_log + алерт |
| C. kv_thrash | KV > 95% И preemptions растут | только алерт (предвестник, не hang) |

Дополнительно: агент недоступен → короткий cooldown 30 с.

**Авто-рестарт:** 2+ hang'а за час → `POST /restart` агенту (Bearer-токен,
ufw по IP), после успеха cooldown 180 с на прогрев.

**Анти-spam:** одно состояние алертится не чаще раза в 10 минут.
Cooldown'ы хранятся в общей БД — шлюз просто не видит смысла запускать
воркеров, пока запись `engine` жива. Экспирация — автоматическая
(`clear_expired` каждый тик).

Боевая проверка: эпизод 2026-08-28 06:13–06:17 МСК — GPU-нода была
недоступна; watchdog поставил quarantine, шлюз не жёг воркеров, после
восстановления — автоматический выход из cooldown. Полный цикл без
участия человека.

### 3.7 Слой E: экономика восстановления

Путь смерти воркера (dead/stuck/loop), карточка не в review:

```
if runs < max_retries:
    if nudged < MAX_NUDGES (=2):
        # ДЁШЕВО: комментарий-пинок + ready, retry_count НЕ трогается
        inject_nudge_comment(reason)
        UPDATE cards SET status='ready', nudged+=1
    else:
        # ДОРОГО: полноценный retry
        UPDATE cards SET status='ready', retry_count+=1, nudged=0
else:
    # ЭСКАЛАЦИЯ: blocked + карточка orchestrator'у
    CREATE card "РАЗБОР БЛОКИРОВКИ: ..." (kind=escalation)
```

Комментарий-пинок формулирован так, чтобы менять поведение, а не повторять
его: «Смени подход — НЕ повторяй ту же последовательность. Упрости шаг,
изолируй проблему, проверяй инкрементально.» Воркер гарантированно его
прочитает: протокол начинается с чтения карточки.

Экономика: 2 бесплатных перезапуска с изменением инструкций → бюджет
retry'ов → человек. На практике большинство шумовых смертей лечится
пинком.

### 3.8 Слой B: декларативные required_gates

Архитектор в корне эпика/задачи объявляет `required_gates="code-reviewer,qa"`
(CSV ролей). Шлюз при закрытии родителя проверяет: на каждую роль есть
дочерняя done-карточка с этим assignee. Нет → родитель не закрывается,
недостающие гейт-карточки создаются автоматически.

Ценность: фиксированный конвейер «обязательно qa + обязательно review»
перенесён из кода в план. Разные эпики требуют разных наборов проверок —
без изменения кода.

### 3.9 Слой C: TraceGuard (борьба с имитацией успеха)

Живёт в fastlane (момент принятия результата). Два уровня:

**L1 — детерминированный (всегда).** Из ARTIFACTS-комментарья
извлекаются все hex-строки длиной 7+ (заявленные коммиты). Каждый хеш
проверяется: `git rev-parse --verify <hash>^{commit}` в центральном
репо. Хеши из worktree видны из центра (общий объект-стор) — ложных
срабатываний нет. Хотя бы один несуществующий → приёмка отложена
(trace_hold), карточка остаётся в review. Карточки без заявленных
коммитов (доклады, отчёты) проверку не проходят — она не применяется.

**L2 — семантический (опционально, `FASTLANE_SEMANTIC_VERIFY=1`).**
Дешёвый LLM-вызов (та же модель, temp 0, max_tokens 400) сверяет
финальный комментарий с журналом событий карточки (последние 15):
«ok=true, если каждое существенное заявление подтверждается журналом;
ok=false при заявлениях о действиях, которых в журнале нет».
Ответ — строго JSON `{ok, issues[]}`. **Fail-open:** любая ошибка
верификатора (сеть, таймаут, мусор в ответе) = уровень пропускается,
приёмка не блокируется. Судья-LLM не имеет права вета — только
право вопроса.

### 3.10 Слой G: allowed_tools

Архитектор задаёт на карточке CSV разрешённых инструментов. Шлюз
вставляет в промпт жёсткую рамку: «разрешены ТОЛЬКО: …; невыполнимо в
рамках → move blocked с объяснением, а НЕ расширяй рамки сам».
Ограничение промпт-уровня; оперативный уровень (permission-map opencode
per-invocation) зарезервирован на развитие. Пусто = ограничений нет.

### 3.11 Слой H: self-review

Против систематической слабости ревью: ревьюер знает, что код написал
«коллега того же семейства моделей», и склонен соглашаться.

Реализация — тройной блок:
1. **Только дифф.** В промпт ревьюера входит инструкция: источник
   истины — `git log --oneline -5` и `git show <sha>` по коммитам
   карточки. Комментарии автора НЕ читать — «они могут вводить в
   заблуждение».
2. **Проверка существования.** Каждая упомянутая в диффе функция/метод/
   класс проверяется на наличие в кодовой базе (grep/read). Отсутствие —
   критическое замечание. Это прямой удар по галлюцинациям «функция
   существует, просто не вижу».
3. **Профиль и температура.** Отдельный агент-профиль (не тот, что писал
   код), температура 0.0.

Эффект: ревьюер технически не может «знать», что код его — он видит
чужой дифф без атрибуции.

### 3.12 Слой J: consult (спрос у роли)

Задача: спросить у специализированной роли вопрос без полной
декомпозиции (не «сделай фичу», а «как правильно спроектировать X»).

Реализация тремя частями:
1. **CLI:** `kb ask <role> "<вопрос>" [--parent]` → карточка
   `kind=consult`, assignee=роль, timeout 45 мин. Роли читаются
   динамически из каталога `roles/` — новая роль появляется без
   изменения кода.
2. **Шлюз:** consult в review получает LIGHT-GATE — штамп `gates-passed`
   без tsc/lint/jest (механический гейт к текстуому ответу неприменим)
   и сознательно БЕЗ ARTIFACTS-штампа (иначе fastlane принял бы карточку
   до ответа воркера).
3. **Fastlane:** приёмка consult — только по `ANSWER:`-комментарию
   именно воркера (`author = assignee`), а не по любому ARTIFACTS.

### 3.13 Слой K: security_gate

Детерминированный скан (не LLM!) для карточек с `security_gate=1`:

- **gitleaks** (бинарник в `tools/`, `detect --no-git` по working tree)
  — секреты. Формат находок: Fingerprint (или File:Line:Rule).
- **npm audit --omit=dev --json** — уязвимости рантайм-зависимостей.
  Формат: `package:severity`.

**Baseline-aware** ровно как механические гейты:
- baseline есть → FAIL только при НОВЫХ находках против
  `gates/sec_gl.txt` / `gates/sec_npm.txt`;
- baseline нет → строгий режим (любые находки = FAIL; для npm —
  high/critical);
- **ошибка самого сканера = FAIL (fail-closed)** — сломанный сканер не
  может пропустить карточку.

Обновление baseline — только явно: `gateway.py --refresh-sec-baseline`
(рука старшего). Тумблер `PIPELINE_SECURITY_SCAN` (в боевом юните = 1).

Боевые числа проекта: 38 находок gitleaks (все в `.env*` — ожидаемо,
секреты лежат в окружении) и 15 уязвимостей npm (9 high) — зафиксированы
в baseline как норма; система реагирует только на рост.

### 3.14 Механические гейты: baseline-aware

`run_gates()` после каждого review (writer/non-writer):

1. `npx tsc --noEmit` → множество `file:line: TS-code`
2. `npm run lint` → множество `file:line`
3. `npm run test:ci` → множество падающих суитов

Сравнение с baseline'ами (`gates/baseline_{tsc,lint,jest}.txt`):
PASS ⇔ нет новых элементов. Исправление части baseline — тоже PASS
(и видно в отчёте: «исправлено: N»). Без baseline — строгий режим
(rc == 0). Отчёт пишется в `runs` (output до 4000 символов) и в
комментарий при FAIL — воркер видит точный список новых ошибок.

### 3.15 Fastlane: правила автоприёмки

Карточка закрывается автоматически, только если ВСЁ:

| № | Правило | Зачем |
|---|---|---|
| 1 | status=review, kind≠epic | область действия |
| 2 | последнее гейт-событие = gates-passed | есть свежая зелень |
| 3 | зелени ≤ 15 минут | не принимать «вчерашнюю» работу |
| 4 | < 2 gates-failed за 60 минут | карточка не «качает» |
| 5 | ARTIFACTS-комментарий (или ANSWER: для consult) | воркер соблюл ритуал |
| 6 | TraceGuard L1 пройден (коммиты существуют) | нет выдуманных артефактов |
| 7 | название не в чёрном списке | чувствительные области — руками |
| 8 | лимит 3 автозакрытия за прогон | скорость ограничена |

Чёрный список (регулярка по названию): secret/token/пароль/auth/crypto/
ротация/migration/docker/deploy/инфра/tsconfig/schema/cert/ssl/jwt —
такие карточки всегда закрывает человек.

Надёжность: 4 попытки с экспоненциальной паузой на `database is locked`
(инцидент 2026-08-26: шлюз держит транзакцию на минуты во время гейтов,
fastlane попадал на лок и умирал, review копился).

### 3.17 Тестирование: рецепт изоляции

Тесты конвейера опасны: неправильный импорт может открыть боевую БД.
Обязательный рецепт (реализован в `tests/test_wave3.py`, 27 тестов):

1. **Env ДО импорта модулей** — PIPELINE_HOME указывает на tempdir,
   иначе константы захватят боевые пути.
2. **ConnProxy** — прокси-класс над sqlite3.Connection с no-op `close()`
   (нативный `Connection.close` — read-only атрибут, monkey-patch
   падает с AttributeError; делегирование через `__getattr__`).
3. **Assert на БД** — каждый тест проверяет, что записи попали в
   TEMP-базу, а не в боевую.
4. **Stubs** — `launch_worker` заменён (никаких реальных opencode),
   `MAX_PARALLEL=0` (никакого запуска).
5. Scratch-БД для миграционных тестов собирается из SCHEMA +
   предшествующих миграций (runtime-колонки W1 применяются заранее).

Регрессия перед боевым применением: реальные сканеры на боевом проекте
(gitleaks/npm), `fastlane.py --dry` на живой доске, целостность доски
до/после.

### 4.3 Типовые инциденты и реакции системы

| Инцидент | Реакция системы |
|---|---|
| Воркер зациклился на команде | loop-детектор: kill группы → nudge с «смени подход» → готов |
| Воркер умер без move | crash-adopt → nudge/retry по экономике |
| Воркер «жив», но молчит >20 мин | heartbeat-stuck → kill группы → путь смерти |
| vLLM завис (запросы есть, токенов нет) | watchdog: cooldown 60 с, шлюз не запускает, алерт в TG |
| GPU-нода недоступна | watchdog: cooldown 30 с, после восстановления — авто-выход |
| 2+ hang'а за час | watchdog: POST /restart агенту, cooldown 180 с |
| Конфликт мержа worktree | abort + blocked + эскалация orchestrator'у |
| Гейты FAIL после мержа | revert мержа, main чист, карточка в todo с отчётом |
| Воркер заявил несуществующий коммит | TraceGuard L1: приёмка отложена |
| Новая утечка секрета | security_gate: FAIL, список NEW_LEAK в отчёте |
| db is locked в fastlane | 4 ретрая с паузами 10/20/30 с |

### 4.4 Уроки, зашитые в дизайн

1. **KV-thrash при MAX_PARALLEL=5** (peak utilization 0.219 → деградация)
   → боевой предел 3; watchdog-pressure-алерт стал индикатором безопасного
   уровня масштабирования.
2. **git 2.43:** `rev-parse --verify <h>{commit}` не работает — только
   `<h>^{commit}`. Зафиксировано в TraceGuard.
3. **Column-level unnamed CHECK** в SQLite не меняется ALTER'ом →
   миграции сложными изменениями = реконструкция таблицы.
4. **flock живёт на fd** — словарь открытых дескрипторов до смерти
   воркера, иначе замок снимается преждевременно.
5. **ARTIFACTS-штамп шлюза на consult** привёл бы к автозакрытию ДО
   ответа воркера — штамп сознательно не ставится, приёмка по ANSWER:.
6. **Baseline обязателен** для любого накопительного сканера: без него
   fail-closed гейт блокировал бы всю доску (38+15 предсуществующих).

## Приложение C. Термины

- **Холодное окно** — момент, когда running=0 и review=0; единственное
  время для изменений инфраструктуры.
- **Baseline** — зафиксированное множество известных дефектов/находок;
  гейты запрещают рост, не требуют нуля.
- **Writer** — роль, модифицирующая код (coder, qa); получает worktree.
- **Gate-карточка** — автоматически созданная карточка декларации
  required_gates.
- **Escalation** — карточка kind=escalation для orchestrator'а: разбор
  блокинга или конфликта мержей.
- **Light-gate** — штамп gates-passed для consult без механических
  проверок.
- **Fail-closed / fail-open** — поведение при ошибке механизма:
  security-сканер при ошибке блокирует (fail-closed), семантический
  верификатор при ошибке пропускает (fail-open). Выбор зависит от цены
  ложного срабатывания.
